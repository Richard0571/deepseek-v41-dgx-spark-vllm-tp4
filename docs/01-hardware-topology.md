# 01 · 硬件与拓扑

**这篇讲什么**：4 台 DGX Spark 的物理连接、地址规划、实测带宽与散热边界 —— 也就是起服前你必须先确认的「物理层事实」。

---

## 1. 节点与地址表

下面这张表是**地址真源**。本文其余文档一律用 `spark-01`…`spark-04` 指代四台节点。

| 逻辑名 | 角色 | 管理口（RJ45，DHCP，会变） | **高速口 RoCE（固定，TP4 用这个）** |
|---|---|---|---|
| `spark-01` | head / rank 0 | `192.168.1.4` | **`10.100.24.4`** |
| `spark-02` | worker / rank 1 | `192.168.1.5` | **`10.100.24.3`** |
| `spark-03` | worker / rank 2 | `192.168.1.6` | **`10.100.24.1`** |
| `spark-04` | worker / rank 3 | `192.168.1.3` | **`10.100.24.2`** |

- 第二轨（同尾）：`10.100.25.4 / .3 / .1 / .2`。
- `HEAD_IP=10.100.24.4`（rank 0 的通信地址，也是 TP 的 rendezvous 地址）。
- 管理口是 DHCP，重启后会换位。**只把它当带外管理入口，不要在脚本里写死管理口 IP。**

### ⚠️ 最容易搞反的一件事

**`10.100.24.x` 的编号顺序与 `spark-0N` 的编号顺序不一致。**

记忆口诀：**02 和 03 是反的**（02 → `.3`，03 → `.1`），01 → `.4`，04 → `.2`。

写任何跨节点脚本前，先 `ssh spark-0N hostname` 反查一次，或直接用上表。历史上按「表面顺序」写脚本会得到
「三台互相连不上、只有一台能通」的假象。

## 2. 网卡

| 项 | 值 |
|---|---|
| 控制器 | **1 张 ConnectX-7**（multi-host 模式，呈现 2 个 PCIe 地址 / 2 个逻辑口），**不是 2 张卡** |
| 高速口网卡名 | `enp1s0f0np0`（轨 24）、`enP2p1s0f0np0`（轨 25） |
| 高速口速率 | `200000` Mb/s（`cat /sys/class/net/<if>/speed`） |
| MTU | 9000（jumbo） |
| 管理口网卡名 | `enP7s7`（1 Gb/s） |

```bash
# 四台一起核
for i in 1 2 3 4; do
  echo "== spark-0$i =="
  ssh spark-0$i 'ip -4 -br addr show | grep -E "10\.100\.|192\.168\."; cat /sys/class/net/enp1s0f0np0/speed'
done
```

## 3. 交换机与接线

| 项 | 值 |
|---|---|
| 交换机 | MikroTik CRS812（或任意带 400G 笼的以太网交换机） |
| 用了几个笼 | **2 个 400G 笼**（每笼走 4 个逻辑口） |
| 线缆 | **2 根「400G QSFP-DD → 2×200G」一分二被动铜缆** |
| 桥接 | 交换机侧把两个笼桥成一个二层域（示例桥名 `br-hs`） |
| **每台只用左 QSFP 笼** | `p1s0f0` + `P2p1s0f0` |

### 右口为什么空着

**右 QSFP 笼是空的，而且建议保持空着。**

每个 Spark 的两个 QSFP 笼**共享同一对 PCIe Gen5 x4 通道**，整卡上限约 **200 Gbit/s** ——
这与「插一条线还是两条线」无关。NCCL 跨同一个口下的两个逻辑接口就能吃满带宽；
插两条线**不会更快**（NVIDIA 工程师口径：无速度优势），还可能因分摊 PCIe 而降 NCCL 性能。
交换机侧也没有余量（空闲端口仅 2×200G + 8×50G）。

> 只有在**要链路冗余**时才考虑接第二口。接线是物理动作，动手前请自行确认。

## 4. 实测带宽与延迟

| 项 | 值 | 条件 |
|---|---|---|
| 单轨带宽 | **约 109 Gbps** | `ib_write_bw` 当场实测（四台一致；轨 24 / 轨 25 / 跨笼都是 109.1） |
| 两轨合计 | **约 218 Gbit/s** | 同上 |
| 端口链路速率 | `200000` Mb/s | `sysfs` 读数，全程未变 |
| 局域网文件分发 | **260–310 MB/s** | `rsync` 走 RoCE，实测（269 GiB 用约 20 分钟） |

> ⚠️ 以上为**已测数字**（A 级）。不要把「端口标称 200 Gb/s」当成「NCCL 实际能到 200 Gb/s」——
> 单轨实测就是 109 Gbps。

## 5. 散热与功耗（实测边界）

四台共享同一套被动散热（12U 机箱 + 机箱风扇 + 交换机自带风扇）。实测结论：

| 项 | 实测范围 | 说明 |
|---|---|---|
| GPU 温度（12 小时窗口） | 均值 **39.6–46.5 °C**，峰值 **72 °C** | 高载段（推理并发 96%） |
| SoC 温度 | 均值 **42.4–52.2 °C**，峰值 **81.9 °C** | 距内核 `critical` trip（**104.8 °C**）仍有 ≥23 °C 裕量 |
| 单机功耗 | 均值 **11–16 W**，峰值 **约 54 W** | 低载 8–10 W |
| 热降频计数 | `HW Thermal Slowdown` **全 0**；`SW Thermal Slowdown` **增量 0** | 跨 37 小时差分基线 |
| 图形钟 | 锁 **300–2200 MHz**，高载死锁在 **2171–2190 MHz** | 无掉频 |

**结论（A 级）**：当前散热方案胜任满载推理，**不需要**为降温改锁频或加散热。

> ⚠️ `nvidia-smi` 的 thermal slowdown 计数是**累计值**，单次读数不能定性——
> 必须做前后差分（间隔数小时）才有意义。
> 同理，GPU 时钟若进入 **latch（慢态，约 700–950 MHz）**，会**静默**污染所有性能数字。
> 起服前的算力 burn 门禁（[`docs/05`](05-preflight.md)）就是为拦这个而设。

## 6. SSH 怎么连

| 从哪连 | 用什么 | 说明 |
|---|---|---|
| 你的工作机 → 节点 | `ssh spark-01` … `ssh spark-04` | 别名来自 NVIDIA Sync 生成的 `ssh_config`，走管理口 |
| **节点之间** | `ssh 10.100.24.x` | **节点上解析不了 `spark-0N` 这类别名**（那份 `ssh_config` 只在你工作机侧）；用高速口 IP，密钥已配免密 |
| 工作机 → 高速口 | ❌ 不通 | 高速口只在本机/节点间可达 |

**跨节点免密是硬前提**：launcher 会把整条 `docker run` 命令经 `ssh` 发到三台 worker 执行。
先验证：

```bash
for ip in 10.100.24.3 10.100.24.1 10.100.24.2; do
  ssh -n -o BatchMode=yes -o ConnectTimeout=5 $ip 'hostname'
done
```

四台都要能免密返回 hostname。任何一台提示要口令，起服就会卡在 worker 阶段。

> 文件换行：跨节点传输的脚本/配置**必须是 LF**。带 CRLF 的文件会让 `set -o pipefail` 报
> `无效的选项名`，或让参数变成 `0.80\r`。推送前后用 `tr -cd '\r' | wc -c` 应为 `0`。

## 7. 起服前的物理层检查清单

- [ ] 四台管理口可达（`ssh spark-0N hostname`）
- [ ] 四台高速口地址与第 1 节表一致（**特别核对 02/03**）
- [ ] 四台高速口 `speed` = `200000`
- [ ] 四台 MTU 9000（`ip -d link show enp1s0f0np0 | grep mtu`）
- [ ] 跨节点免密：四台 `ssh -o BatchMode=yes` 通
- [ ] 交换机两个 400G 笼 `link up`，桥内四台可见
- [ ] 四台 NVMe 可用空间 ≥ 权重 + Engram 表所需（见 [`docs/03`](03-model-preparation.md)）
- [ ] 四台 `nvidia-smi` 能出结果，且时钟不在 latch 慢态
