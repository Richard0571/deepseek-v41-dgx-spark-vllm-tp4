# 03 · 模型准备：分片、Engram 离 GPU、分发

**这篇讲什么**：把一个几百 GB 的 MoE 检查点铺到四台机器上，并算出「留给 KV cache 的余量」——顺序是：先算账，再决定哪些权重能留在 GPU 侧、哪些必须搬到本地 NVMe。

---

## 1. 对象

| 项 | 值 |
|---|---|
| 模型 | **DeepSeek-V4.1-Flash** |
| 本地路径 | `<MODEL_DIR>`（**四台必须完全相同**） |
| 量化声明 | `quant_method = fp8` / `weight_block_size = [32, 32]` / `scale_fmt = ue8m0` / `expert_dtype = fp4` |
| 分片数 | **48** 个 `*.safetensors`（每台一份完整 48 片） |

> 说明：这是「dense / 投影走 MXFP8、路由专家走 FP4」的混合量化，**不是**清一色 FP4。
> 这一点很重要：它决定了引擎里 `wo_a.weight_block_size` 之类的分支取值，也决定了 block size 的选择（见 [`docs/06`](06-launch-parameters.md)）。
> 换检查点时请先读 `config.json`，确认这三行一致，再谈别的。

## 2. 先算账：为什么 Engram 表必须离开 GPU

TP4 是**每台一份完整权重**（不是把权重切四份）。所以每台要装下整个检查点。

| 项 | 数值 |
|---|---|
| 全权重 | **510.29 GB** |
| —— 非 Engram 部分 | **307.22 GB** |
| —— **Engram n-gram 表** | **203.07 GB（占 40%）** |
| 四台物理内存合计 | 4 × 128 GB = **512 GB** |

```
510.29 / 512 = 99.7%
```

**全权重几乎等于四台物理内存之和。** 如果 Engram 表也留在内存里，KV cache 一点空间都没有。

### ⚠️ 统一内存让这件事更糟

GB10 **没有独立 HBM**，host 内存与 GPU 内存是**同一块 128 GB**。
所以「把 Engram 表放 host memory」这个在普通服务器上很常规的优化，**在 Spark 上不省物理容量**：

| 做法 | 在 Spark 上省不省内存 |
|---|---|
| Engram 表放 host memory | ❌ **不省**（host 与 GPU 是同一块） |
| **Engram 表放本地 NVMe（SSD offload）** | ✅ **这是唯一真正腾出容量的手段** |

### 结论：路线与余量

| 路线 | 每台权重 | 每台留给 KV / 激活 | 可行性 |
|---|---|---|---|
| **A. 保持现有 FP8 专家（零额外下载）** | **76.8 GB** | **约 51 GB** | ✅ 推荐起点 |
| B. 专家再量化到 FP4（需自己做） | 约 40 GB | 约 88 GB | ✅ 余量更大，但要多一道工序 |

本指南按**路线 A** 展开（现有权重直接可用）。

实测 KV 口径（A 级）：本配置下 vLLM 侧的 KV 约 **5.17–5.19 KB/token**。
⚠️ 不要用官方卡上那个「890 B/token」的理论值来推算 vLLM 的池 —— 实测池里含投机草稿 + SWA + indexer 页，
两者口径不同，混用会把池算大三倍以上。

按 5.18 KB/token：一条 614,400 token 的请求至少需要约 **3.18 GB**；要 2.3 倍并发则需约 **7.3 GB**。
这就是第 2 节算出来的「约 51 GB 余量」要覆盖的东西。

## 3. Engram 表搬到本地 NVMe（node-local rows）

这是**硬前提，不是优化**。步骤：

1. 每台准备本地目录，例如 `/var/tmp/<模型名>-engram-local`。
2. 把 Engram 表按**本地分片**落到该目录（只放本 rank 需要的那部分行，不必整表）。
3. 起服时以**只读 bind mount** 挂进容器，并用环境变量指到该目录。

```bash
# 每台：确认空间与落盘完成
df -h /var/tmp
ls /var/tmp/<模型名>-engram-local | head
```

### ⚠️ 一个极具欺骗性的 bug：rank-offset

**Engram 检查点存的是「整表」，而调用方传的是「rank-local 行号」。**
如果读表时不加本 rank 的行偏移，**rank 1–3 会去读 rank 0 的行**。

| 症状 | 说明 |
|---|---|
| 输出仍然像正常文本 | ✅ 看不出来 |
| 冒烟测试能过 | ✅ 看不出来 |
| 吞吐不受影响 | ✅ 看不出来 |
| **只能靠逐行对拍发现** | ❌ 这是唯一的判据 |

**应对**：起服**必须**跑一次「印行对拍」——
同一批行号在四个 rank 上 lookup，比对结果；四个 rank 全 MATCH 才算通过。
对拍方法与判据见 [`docs/08`](08-verification.md)。

> 修复后有一个副作用要知道：Engram 行的页缓存可能涨到约 4 倍（因为不再共享 rank 0 的行）。
> 这也是为什么 [`docs/02`](02-host-preparation.md) 的哨兵阈值必须是 1024 MB 而不是更大。

## 4. 四台分发（走局域网，不走公网）

**先在 1 台下载完，再用局域网分发到其余三台。**

| 段 | 走哪条路 | 实测速度 |
|---|---|---|
| 公网 → `spark-01` | 镜像源直连（见第 5 节） | 取决于源 |
| `spark-01` → 02/03/04 | **RoCE `rsync`** | **260–310 MB/s**（269 GiB 约 20 分钟） |

```bash
# 一台下载完后，分发（注意：必须 LF 换行的脚本；后台启动用 setsid）
rsync -a --info=progress2 <MODEL_DIR>/ cq@10.100.24.3:<MODEL_DIR>/
```

**不要在工作机中转大文件。** 工作机的出口很可能经过计量代理，一个大模型就能吃掉整个月的流量。

## 5. 下载纪律（硬约束）

> **禁止**用「计量代理 / 订阅节点 / 任何指向代理的环境变量出口」下载**单次任务总量 > 5 GB** 的内容。

按**单次任务的总下载量**算，不是单文件：

| 场景 | 是否禁止 |
|---|---|
| 单个 6 GB 文件 | ❌ 禁止走代理 |
| 10 个 800 MB 文件（合计 8 GB） | ❌ 禁止走代理 |
| 单个 4 GB 文件 | ✅ 允许 |
| 分片下载合计 < 5 GB | ✅ 允许 |

### 优先级

| 优先级 | 路径 |
|---|---|
| 1 | **局域网传输**（RoCE / 千兆）—— 完全不占外网 |
| 2 | **明确绕过代理的直连** |
| 3 | **镜像源**（前提是不经代理） |
| 4 | 都不行 ⇒ **停下来问**，不要擅自走代理 |

### 动手前必查

```bash
# 1) 查代理环境变量
env | grep -i proxy

# 2) 查本地代理端口是否在监听
ss -ltnp | grep -E '7890|7891|1080'

# 3) 无代理直连测试
curl -sI --noproxy '*' --max-time 15 <你的镜像站> | head -1
```

对节点而言，「代理环境变量为空」通常就够了（节点一般不配系统级代理）。
但**如果你在工作机上做下载**，注意：**环境变量为空 ≠ 没走代理** ——
工作机的图形/系统级代理设置可能对某些 HTTP 客户端自动生效。
判据是**不对称现象**：同一个 URL，A 客户端全失败而 B 客户端高速成功 ⇒
先怀疑「其中一个读了系统代理」，而不是「B 工具更快」。

### 镜像源的两个坑

| 坑 | 现象 | 处置 |
|---|---|---|
| 某些传输后端不可用 | 报 `401 Unauthorized`（指向某个 CAS 域名） | 显式禁用该后端（设对应的环境变量为 `1`） |
| 官方域名被针对性阻断 | 直连必超时；DNS 解析到无关网段 | 用可直连的镜像站，或换成局域网内已有的副本 |

下载完在交接文档里记一笔：**内容 + 大小 + 走的哪条路**。

## 6. 就位后的验收

```bash
# 每台：分片数、总字节、索引一致
for i in 1 2 3 4; do
  echo -n "spark-0$i shards="; ssh spark-0$i "ls <MODEL_DIR>/*.safetensors | wc -l"
done

# 索引文件的 total_size 应在四台一致
for i in 1 2 3 4; do
  ssh spark-0$i "python3 -c \"import json;print(json.load(open('<MODEL_DIR>/model.safetensors.index.json'))['metadata']['total_size'])\""
done
```

期望：**48 / 48**，四台的 `total_size` 完全相同。

再抽最大的一片做字节核对（这是「四台字节一致」的最强证据）：

```bash
ssh spark-01 "stat -c %s <MODEL_DIR>/model-00048-of-00048.safetensors"
for i in 2 3 4; do
  ssh spark-0$i "stat -c %s <MODEL_DIR>/model-00048-of-00048.safetensors"
done
```

### 就位检查清单

- [ ] 四台 `<MODEL_DIR>` 路径完全相同
- [ ] 四台分片数均为 48/48
- [ ] 四台 `index.json` 的 `total_size` 相同
- [ ] 抽检最大分片字节数四台相同
- [ ] 四台 Engram 本地目录已铺好（各含本 rank 的行）
- [ ] 四台本地盘剩余空间 ≥ 后续镜像与缓存的预留
- [ ] `config.json` 的量化声明与第 1 节一致
