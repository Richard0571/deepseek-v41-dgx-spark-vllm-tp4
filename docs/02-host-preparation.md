# 02 · 宿主侧前置：内核护栏与内存哨兵

**这篇讲什么**：起服之前必须在**宿主**（不是容器里）做好的两件事 —— 内核内存护栏、以及一个会在内存触顶前**主动杀掉容器**的哨兵。这两件是这套部署里唯一真正防「机器假死」的机制。

---

## 1. 为什么宿主侧要单独做一层

容器里能做的保护（OOM killer、cgroup limit）在本硬件上**不够用**，原因有三：

1. **统一内存**：GB10 的 host 内存和 GPU 内存是同一块物理内存。GPU 侧的分配会推高宿主的内存压力，
   但它**不一定计入容器的 cgroup 记账** —— 容器看起来「才用了 60 GB」，宿主已经在触顶。
2. **触顶不是干净的 OOM**：内核对这种「回收赶不上分配」的状态不会触发 OOM killer，
   而是进入 `reclaim thrash` —— 连 `sshd` 都无法完成握手。这就是本文所说的 **wedge**。
3. **没有带外管理**：DGX Spark **没有 BMC / IPMI**。一旦 wedge，只能**物理断电**。

所以护栏要分成两层：**内核侧留出回收余量** + **宿主侧主动干预**。缺一不可。

---

## 2. 内核护栏

写入 `/etc/sysctl.d/99-tp4-guard.conf`（**四台都要**）：

```ini
vm.min_free_kbytes = 1048576
vm.watermark_scale_factor = 200
```

生效与复核：

```bash
sysctl --system
sysctl vm.min_free_kbytes vm.watermark_scale_factor
# 期望输出：1048576 与 200
```

### 为什么是这两个值

| 参数 | 取值 | 理由 |
|---|---|---|
| `vm.min_free_kbytes` | **1048576**（= 1 GiB） | 内核默认值只有**几十 MB 量级**。在 121.7 GiB 的机器上留这么少，回收线程来不及在分配洪峰前腾出页，这是 wedge 的主因之一。抬到 1 GiB 让内核始终保有一个可回收池。 |
| `vm.watermark_scale_factor` | **200** | 拉大 `low`/`high` 水位之间的间距，让 kswapd 更早开始回收、并且有更长的缓冲带，而不是等到 `min` 水位才紧急回收。 |

### 验证护栏确实生效（不要只看文件存在）

```bash
# 逐台核对运行时值，而不是只核对文件
for i in 1 2 3 4; do
  echo -n "spark-0$i: "
  ssh spark-0$i 'cat /proc/sys/vm/min_free_kbytes /proc/sys/vm/watermark_scale_factor | tr "\n" " "; echo'
done
```

同时确认**没有其它文件覆盖**：

```bash
grep -rn "vm\.min_free_kbytes\|vm\.watermark" /etc/sysctl.conf /etc/sysctl.d/
```

应该**只命中**你写的那一份。若还有其它来源，以后者为准（文件名排序），护栏可能被静默改掉。

## 3. 宿主侧内存哨兵（memguard）

### 3.1 它做什么

一个脱离终端的常驻进程，每 `INTERVAL` 秒读一次本机内存水位与内核内存压力指标（PSI），
满足触发条件时**立刻 `docker kill` 本机容器**。

把「不可恢复的 wedge」换成「可恢复的容器死亡」—— 这是它存在的全部意义。

### 3.2 两相位判据

本配置**不是一个固定阈值**，而是两个相位：

#### 相位 A · 加载期（刚起服、正在读权重、正在编译）

```
kill = (MemAvailable < ABS)
       OR
       (MemAvailable < PSI_HARD_ABS  AND  PSI_full_avg10 > PSI_HARD)
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `ABS` | **1024 MB** | 绝对下限，**独立 OR 支**，任何情况下都生效 |
| `PSI_HARD_ABS` | **16 GiB** | 合取支的水位前提 |
| `PSI_HARD` | **50.0** | 加载期内存压力上限 |
| `INTERVAL` | **2 s** | 加载期采样要密 |

#### 相位 B · 稳态（服务就绪且**已静默一段时间**）

```
kill = (MemAvailable < ABS)
       OR
       (PSI_full_avg10 > 5.0)
       OR
       (PSI_some_avg10 > 60.0)
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `ABS` | **1024 MB** | **与加载期相同**，硬约束下限 |
| `PSI_full` | **5.0** | 稳态真 thrash 判据 |
| `PSI_some` | **60.0** | 部分任务受影响的兜底 |
| `INTERVAL` | **2 s** | |

### 3.3 为什么必须分相位（这是最关键的设计点）

实测数字（A 级，读宿主哨兵日志）：

| 场景 | `PSI_full_avg10` 实测 |
|---|---|
| 完全空闲 | **0.00** |
| **加载 / 预热期峰值** | **28.1 – 39.6** |

加载一个 475 GiB 的检查点到只有几十 GiB 余量的机器里，**页缓存回收导致的 full 压力结构性偏高**，
这是正常且预期的。如果加载期也用稳态的 `PSI_full > 5.0`，**一开服就会被自己杀掉**。

所以：

- **加载期**用「绝对下限 + 极高的 PSI 门槛（50）」；
- **就绪且静默 ≥ 300 s 之后**才切到稳态的「PSI 5.0 / 60.0」。

### 3.4 静默闸：为什么是 300 s 而不是「就绪即切」

实测的起服脚本在 `/v1/models` 返回 200 之后，还有约 **140 s** 的空窗
（稳态观察 `sleep` + 装载后页缓存回收 + 短等待），**之后才开始长上下文预热**。

如果按「就绪即切」处理，会在那 140 s 空窗内切到 `PSI 5.0`，
紧接着的预热（PSI 28–40）会**立刻打死服务**。

`300 s > 140 s` ⇒ 预热一开跑，静默计时即清零，**只有真正长静默之后才切稳态**。

> 静默的定义：引擎的 `num_requests_running + num_requests_waiting == 0` 连续保持 ≥ 300 s。
> ⚠️ **必须校验「指标真的取到了」**：如果 `/metrics` 取不到，一个朴素的 `awk` 求和会打印 `0`，
> 把「服务不可达」误判成「服务静默」。切换前必须先确认服务可达**且** `/metrics` 里含预期的指标前缀。

## 4. ⚠️ 绝对下限为什么是 1024 MB，而不是 8192 MB

**这是本指南最容易被「照抄」搞坏的一处。**

| 直觉做法 | 后果 |
|---|---|
| 设 `ABS = 8192 MB`（「留 8 GB 才安全」） | **几秒内误杀**：本配置在稳态正常运行时，head 的 `MemAvailable` 就只有 **1.6–5 GiB**（实测 1.58–4.8 GiB）。8 GB 的门槛在任何时刻都满足触发条件。 |
| 设 `ABS = 1024 MB` | 正确。它与「击杀线」同量级，只在真的接近触顶时才动作。 |

**推论**：**1024 MB 是硬下限，不得放宽、不得停用、不得修改。**
不要把「想更安全」理解成「把阈值调高」—— 那会让哨兵从保命变成自伤。

### 阈值定档速查

| 参数 | 加载期 | 稳态 | 可否调整 |
|---|---|---|---|
| 绝对下限 `ABS` | 1024 MB | 1024 MB | ❌ **不得放宽**（可以更大，但没有意义） |
| PSI 门槛 | 50.0 | 5.0 / 60.0 | 可调，但要先读懂第 3.3 节 |
| 采样间隔 | 2 s | 2 s | 可调 |
| 静默时长 | — | 300 s | 可调（演练时可调小以便观察切换） |

**不要照抄别人的 8192 / 16 GiB 这类值** —— 那些来自 head 余量有 16–24 GiB 的其它配置，
在统一内存机上不适用。

## 5. 用法

```bash
# 起哨兵（加载期）
bash /home/<USER>/memguard.sh start <容器名> 1024 2 5.0 60.0

# 查看在岗状态（含 pid 与当前判据）
bash /home/<USER>/memguard.sh status <容器名>

# 停
bash /home/<USER>/memguard.sh stop <容器名>
```

启动后**必须**做三件事：

1. **确认真的起来了**：`status` 返回「运行中」，且 pidfile 里的 pid 与 `ps` 实际进程一致。
   ⚠️ 常见缺陷：脚本用 `pgrep` 找自己的 `__watch` 进程，**找不到时不写 pidfile、却仍打印「已启动」并 `exit 0`**。
   这会产生「容器在跑、哨兵没在跑、却没有任何报错」的状态。
   **修法**：哨兵启动失败时 `exit 3`；调用方（起服脚本）检查返回码，失败即**拒绝起服**。
2. **确认进程脱离了 SSH 会话**：用 `setsid` 启动，然后断开 SSH 再 `status` 一次，仍为「运行中」。
3. **记录本次击杀计数的基线**（见第 7 节）。

---

## 6. 四台协调清场（防「半死态」）

单台哨兵只能杀**本机**容器。TP4 里一台被杀掉、另外三台还活着 ⇒ 进入
**「head 死 / worker 活」的半死态**，此时既没有可用服务，也没法直接重启（会撞上残留进程）。

**设计**：哨兵触发时

1. **先本机保底 kill**（绝不因为协调器不可用而延后）；
2. 再**尽力**调用一个四台协调清场脚本（`flock` 保证重复触发幂等），失败则记录「可能残留半死态」并继续。

**清场脚本的要求**：四台统一 `docker kill` + `docker rm -f`，任一节点 SSH 失败要回非零，
且**必须同时停掉两个相位的哨兵**（否则残留的稳态哨兵会在下一轮加载期按 `PSI 5.0` 反杀新容器）。

> ⚠️ 这条「同时停两个哨兵」是踩过坑的：两个相位的哨兵 pidfile 不同名，可以并存。
> 若清场只停加载期哨兵，残留的稳态哨兵会在新容器加载期开火。

---

## 7. 击杀计数怎么读（容易被骗）

哨兵日志**跨 boot 追加**，且每个击杀事件占**两行**（`!! 触发：…` + `触发前水位 …`），
分隔行里还含「保留历史**触发**证据」字样。

| 写法 | 结果 |
|---|---|
| `grep -c 触发 <log>` | ❌ 把分隔行与水位行都算进去（实测 6 行 / 实际只有 2 次击杀） |
| `grep -c '!! 触发：' <log>` | ✅ 正确 |

**每次起服前记一次基线，收尾时算增量**；不要读「累计总数」当本次结果。

另外：哨兵重启时**不要清空日志**（`> "$LOG"`）。那会把刚发生的击杀证据抹掉，
与「留证据」的目的正好相反。改成 append + 轮转。

## 8. 起服标准流程（模板）

```bash
# 0. 核护栏（运行时值，不是文件）
sysctl vm.min_free_kbytes vm.watermark_scale_factor     # 期望 1048576 200

# 1. 清场：四个节点一起，且两个相位的哨兵都停
bash <KILL_ALL_SCRIPT> <容器名>

# 2. 挂哨兵（加载期）
bash /home/<USER>/memguard.sh start <容器名> 1024 2 5.0 60.0 || { echo "哨兵起不来，拒绝起服"; exit 1; }
bash /home/<USER>/memguard.sh status <容器名>            # 必须看到「运行中」

# 3. 起服（此时才允许创建容器）
bash <BOOT_SCRIPT>

# 4. 全程盯哨兵日志与容器日志
tail -f /home/<USER>/logs/memguard-load-<容器名>.log
```

**第 2 步失败就不许进第 3 步。** 这是「无哨兵不起服」的落地方式。

> 有条件的做法是把第 2 步做成**机器门闩**（脚本读返回码），而不是靠人记得。
> 曾经的缺陷正是「靠人记得」：起服脚本调用哨兵启动后**不检查返回码**，于是「无哨兵起服」在代码路径上是敞开的。

---

## 9. 收工后

- 停哨兵：`memguard.sh stop <容器名>`（两个相位都要停）。
- 释放独占声明（见 [`docs/09`](09-rollback.md)）—— **不释放会卡住后续流程**。
- 四台一起清场，避免半死态。
