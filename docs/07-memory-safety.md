# 07 · 统一内存的失效模式与内存安全

**这篇讲什么**：这套硬件最危险的失效模式（**wedge**）长什么样、为什么会发生、怎么在它发生前干预，以及如何避免把「读盘放大」误判成「内存泄漏」。

---

## 1. 前提：没有独立显存

| 项 | 值 |
|---|---|
| `MemTotal` | 127,600,812 kB = **121.69 GiB** |
| 结构 | host 内存与 GPU 内存是**同一块** LPDDR5X |
| 独立 HBM | **没有** |

推论（每一条都会反复影响你的决策）：

1. 「把数据放 host 内存」**不省容量** —— 它和 GPU 抢同一块。
2. GPU 侧的大额分配会推高宿主内存压力，但**不一定计入容器 cgroup 记账**
   ⇒ 容器看起来「才用了一半」，宿主已经在触顶。
3. 权重 + KV cache + 激活 + 通信缓冲，全在一个池子里。**一个 500 GB 的检查点占了 99.7% 的物理内存**
   （见 [`docs/03`](03-model-preparation.md)），所以余量永远是「几 GB」这个量级。

## 2. ⚠️ wedge：那种只能物理断电的状态

### 2.1 指纹（记住这张表）

| 项 | 状态 |
|---|---|
| `ping` | ✅ **通** |
| TCP `:22` | ✅ **接受连接** |
| **SSH banner** | ❌ **超时**（永远走不完握手） |
| HTTP 服务 | ❌ 无响应 |
| OOM killer 记录 | ❌ **没有**（这不是干净的 OOM） |
| 自愈 | 25–40 分钟，或**断电** |

**「ping 通 + TCP 连得上 + SSH 走不完 banner」= wedge。**

### 2.2 成因

不是「内存不够」，而是**回收来不及**：

统一的 `anon` 页加上驱动侧持有的页把系统推到触顶时，内核进入 **reclaim thrash** ——
它一直在回收，但回收速率赶不上分配速率。这种状态下连 `sshd` 分配不到足够内存完成握手。

**所以防它靠两件事：给内核留出回收余量 + 外部主动干预。不是靠「少用点内存」。**

### 2.3 为什么后果这么重

**DGX Spark 没有 BMC / IPMI。** 一旦 wedge，**只能人工物理断电**。

### 2.4 出事时的处置（按序）

1. **停手** —— 不要再起新容器、不要反复重试。
2. 从**另一台**节点探（`ping` + `ssh`），确认是单台还是全部。
3. **⛔ 不要轮询 SSH。** 对已 wedge 的节点反复连接会堆起几百个会话，**拖慢恢复**。
4. 等 25–40 分钟看是否自愈。
5. 不自愈 ⇒ **报给能动手的人去断电**，写清哪几台、IP、当前状态。
6. 恢复后先核 `ip -4 -br addr`（管理口 DHCP 会换位）与四台健康，再继续。

## 3. 三层防护

| 层 | 内容 | 详见 |
|---|---|---|
| 1 | **内核护栏**：留出回收余量 | [`docs/02`](02-host-preparation.md) §2 |
| 2 | **宿主侧哨兵**：触顶前主动杀容器 | [`docs/02`](02-host-preparation.md) §3 |
| 3 | **容量旋钮**：把平台余量本身调厚 | [`docs/06`](06-launch-parameters.md) §3 |

三者叠加才叫「尽最大可能避免断电」。任何一层缺失，都只是概率问题。

### 关键数字

| 项 | 值 |
|---|---|
| 内核护栏 | `min_free_kbytes = 1048576`、`watermark_scale_factor = 200` |
| 哨兵绝对下限 | **1024 MB**（**硬约束，不得放宽**） |
| 真实 wedge 时的读数 | `MemFree` 崩到 **591 MB**、`MemAvailable` = **0**（页缓存从 34.3 GB 掉到 0.33 GB） |
| 常规（正常）击杀时的读数 | `MemFree` 还有 **6.2–9.9 GB** |

⇒ **危险边界在 `MemFree` 的低处**。不要用「`MemFree` 看起来还很多」当安全依据。

> ⚠️ 也不要为了「更早发现」就把阈值调高。原因见 [`docs/02`](02-host-preparation.md) §4：
> 本配置稳态余量本就只有 1.6–5 GiB，门槛设成 8 GiB 会**在几秒内误杀**。

## 4. 宿主内存账本（怎么读读数）

```
MemAvailable ≈ MemFree − d,   d ≈ 5.85–5.92 GiB（实测）
```

- `d` 与 `watermark_boost` **无关**：一次实测里 boost 从 0 拉到 1,864 MiB 期间，`d` 只动了 **15.2 MB**
  （因为 `pagecache/2` 小于 `wmark_low`，内核 `si_mem_available()` 的 `min()` 取前者，boost 被旁路）。
  ⇒ **不是「记账假跌」。**
- 有一个常见推导：`未记账量 = MemTotal − MemFree − (已列举项之和)`。
  ⚠️ **这是残差，不是直测量。** 它包含「按设计占用的容量」，也包含未列举的内核分配。
  **不要把它命名为「某个具体池」**，更不要据此下结论。
- 内核侧的回收机制**已被排除**为成因：残差的变化与 `pgmigrate` / `compact` / `pgscan` / `pglazyfreed`
  的相关系数 |r| ≤ 0.025；大额释放时多为 0。⇒ 释放路径在驱动内部，不在内核账上。

### 「空置」不等于空

引擎在**零请求**下仍然在跑 step。所以「没人用」的时候内存也在动，不要用「应该闲着」当推理前提。

## 5. ⛔ 读盘放大：会伪装成内存泄漏

**这是本指南最值得单独记一条的坑。**

在放着几百 GB 模型文件的目录上做**递归扫描**（`grep -r` / `rg` / `find -exec` / `du -a`），
会把页缓存以极高速度灌满，把内存监控打成锯齿，并**伪造出「内存持续漂移」的假象**。

### 现场实录

```text
PID      ELAPSED  STAT  COMMAND
1147701  57:41    R     grep -rl 'guard: head' /home/<USER>/
read_bytes: 2,888,468,189,184 (2.888 TB)   write_bytes: 0
```

- 来源：一次**诊断用的单行命令**。
- 因为 `| head -30` 没凑够 30 个命中，`grep` **不提前退出**，把整棵模型树读完了。
- 持续 **58 分钟**，速率约 **840 MB/s**。

### 症状（完全可以冒充内存问题）

| 时刻 | `MemAvailable` | `free` | `cached` | `anon` |
|---|---|---|---|---|
| T1 | 4,632 MB | 8,975 | 4,471 | 8,480 |
| T2 | 6,179 MB | 11,921 | 1,670 | 8,492 |
| T3 | 3,160 MB | 6,128 | 7,218 | 8,497 |

**关键判据：`anon` 平得像尺子（4 分钟只动 17 MB），摆动全在 `free` ↔ `cached` 之间。**
⇒ 这不是内存泄漏，是页缓存被反复灌满/回收。

清掉进程后即时恢复：`MemAvailable` 3,024 → **6,515 MB**；`anon` 8,480 → 5,428 MB。

### 判据表（判「内存泄漏」前必须先排除读放大）

| 特征 | 读放大（页缓存） | 真泄漏（`anon`） |
|---|---|---|
| `anon` / `AnonPages` | **平** | **单调涨** |
| `cached` | 大幅摆动 | 缓慢变 |
| 磁盘 `read_bytes` 增速 | **几百 MB/s** | 低 |
| 清掉进程后 | **立刻恢复（GB 级）** | 不恢复 |

### 规矩

```bash
# ❌ 全部禁止（会读穿整棵模型树）
grep -r … <MODEL_ROOT>/
rg … <MODEL_ROOT>/
find <MODEL_ROOT> -exec … \;
du -a <MODEL_ROOT>

# ✅ 只搜具体文件或明确的小目录
grep -n "…" <MODEL_ROOT>/*.sh
grep -n "…" <LOG_DIR>/*.log
grep -rn --include=*.py … <容器内某个有界代码目录>
```

### 一条可复用的诊断命令（按读盘量排序找跑飞进程）

```bash
for p in $(ps -eo pid= --no-headers); do
  rb=$(awk '/^read_bytes/{print $2}' /proc/$p/io 2>/dev/null) || continue
  echo "$rb $p $(tr -d '\0' < /proc/$p/cmdline 2>/dev/null | cut -c1-80)"
done | sort -rn | head
```

两次采样求差 → MB/10s，最直观。

⚠️ **诊断命令也别用 `| head -N` 之后就丢下不管**：`head` 提前退出会让上游收到信号，
但上游若已进入大目录可能**继续读**。跑之前先想「它要读多少」，跑完确认进程真的没了。

## 6. 长上下文与余量：把「被击杀」做成「稳定通过」

把长上下文从「被杀」做到「稳定通过」的**正确路径**（不是调高哨兵阈值）：

| # | 动作 | 效果 |
|---|---|---|
| 1 | 清掉读放大进程（第 5 节） | 立即换回数 GB 的 `MemAvailable` |
| 2 | 起服前 / 装载后各做一次页缓存回收 | 让「起服瞬间的页缓存状态」确定化 |
| 3 | 降低 KVB（`--kv-cache-memory-bytes`）一档换余量 | 每次约 +1 GB 平台余量 |
| 4 | 把 `--max-num-batched-tokens` 降到 2048 | KV 多 5.2%、余量多约 2.8 GB |
| 5 | 预热门值设合理（不是越高越好） | 门太高会让「跳过预热」成为默认，反而失去保护 |

### 实测验收（A 级，单 boot）

| 项 | 值 |
|---|---|
| 614,400 档单请求 | **通过**（实测 617,166 tokens，TTFT 537.2 s，1,149.0 tok/s） |
| 该档全程最低 `avail` | **4,562 MB**（= 击杀线 1024 MB 的 **4.5×**，连续采样最低值） |
| 本 boot 新增击杀 | **0** |
| 半死态 | 无（四台容器 `Running`、`Restarts=0`） |

> ⚠️ `avail` 必须看**连续采样的最低值**，不能看单点。单点会被锯齿误导
> （实测记录过 1,042 / 1,043 / 1,044 / 1,045 / 1,075 / 1,081 / 1,086 / 1,092 MB 这样一串）。

### 水位门与「跳过预热」

起服脚本应在开始长上下文预热前检查 head 的 `MemAvailable`：

- 足够 ⇒ 正常预热；
- **不足** ⇒ 先尝试回收页缓存（最多几轮）；
- 仍不足 ⇒ **打醒目提示 + 写一个 `short-only` 标记 + 状态置 `LOWHEAD`**，
  含义是「**本次 boot 仅短请求可用**」，**不得标记为已验收**。

最后这条很重要：**静默降级比明确失败更危险**。宁可让运维看到「本次不可长上下文」，
也不要让第一个真实长请求去撞判据。

## 7. 内存安全检查清单

- [ ] 四台 `sysctl` 运行时值 = `1048576` / `200`
- [ ] 没有任何其它配置文件覆盖护栏
- [ ] 哨兵在岗（两个相位都确认过），且 pidfile 与 `ps` 一致
- [ ] 哨兵绝对下限 = **1024 MB**（**没被改成 8192 一类的大值**）
- [ ] 本 boot 的击杀基线已记录（用 `!! 触发：` 前缀计数）
- [ ] 没有任何进程在模型目录上做递归扫描
- [ ] 起服前已做页缓存回收，且**失败可见**（不是静默吞掉）
- [ ] 长上下文验收记录的是**连续采样最低 `avail`**，不是单点读数
- [ ] 若本次是 `LOWHEAD` / `short-only`，已明确标注「未验收长上下文」
- [ ] 收工后两个相位的哨兵都已停、独占声明已释放
