# 12 · 引擎运行时行为（两条反直觉的坑）

**这篇讲什么**：prefix cache 的真实复用与驱逐行为，以及「请求带 tools 时引擎会强制保留历史思考」这条被硬编码的行为。这两条都不是参数问题，但都会显著影响延迟预算与容量规划 —— 而且都是**直觉会猜反**的那种。

> 两条结论都来自**引擎源码 + 受控实测**，不是猜测。改动引擎版本后需要重新核。

---

## 1. ⭐ 运行时行为：prefix cache 的真实表现（反直觉）

这一节是**唯一一处不要相信直觉**的地方。

### 1.1 引擎配置（A 级，读 `/metrics` 的 `cache_config_info`）

```text
enable_prefix_caching="True"
block_size="64"                          # ⚠️ 与启动参数 --block-size 128 不是同一个字段
prefix_caching_hash_algo="sha256"
kv_cache_size_tokens="1722343"
num_gpu_blocks="42679"
kv_cache_memory_bytes="5900000000"
prefix_cache_retention_interval="0"
```

> ⚠️ 上面 `block_size=64` 与启动参数 `--block-size 128` **不是同一个东西**，
> 具体块算术**尚未定论**（见第 1.5 节）。引用时请把两个值分开写。

### 1.2 「前缀没变 ⇒ 缓存必中」**不成立**

受控实测（串行、并发 1、`max_tokens=1`）：

| 组 | prompt tokens | 第 1 次 | 第 2 次 | 第 3 次 | 自复用 |
|---|---|---|---|---|---|
| S | 12,288 | cached 0 / 4,811 ms | **12,160 / 225 ms** | **12,160 / 229 ms** | ✅ 99% |
| L | 27,189 | cached 0 / 10,483 ms | **0 / 10,542 ms** | **0 / 10,895 ms** | ❌ **0%** |

**同一尺寸、同一内容、间隔 1 秒，命中与否都不稳定。**
中间尺寸也不干净（12,288 / 13,167 / 17,498 能命中；14,891 / 20,748 / 27,189 / 32,772 不能）——
**没有干净的「尺寸阈值」**。

### 1.3 正确表述只有两句

1. **一个「头」能被整段复用** —— 实测同一个头（24,713 tokens）在 **43 秒 / 4.4 分钟**间隔下
   `cached/全量 = 24,704/24,713 = 99.96%`。
2. **条目会在数分钟内从缓存里消失** —— 同一个头在 **5.5 分钟 / 17 分钟**后为 `0`。

所以「引擎留不住大前缀」「头每轮必丢」**都不成立**。停顿只在**条目已被驱逐**时发生。

⚠️ **但「数分钟内消失」的触发条件尚未核验**，不要把它当已定论。

### 1.4 驱逐机制（源码级，A 级）

| 事实 | 说明 |
|---|---|
| **只有一个全局池** | 所有 KV 组共用一个 block pool |
| **分配是唯一的带内驱逐点** | `get_new_blocks()` 在池饱和时按 **LRU** 弹出 |
| **释放 ≠ 驱逐** | 请求结束只把块放回 free 队列**尾部**，**哈希保留**（还能被别的请求命中） |
| **运行中的块不可驱逐** | `ref_cnt > 0` 的块不在队列里 |
| **空闲期 / 定时 / TTL 驱逐：没有** | 引擎空闲时什么都不做 |
| **整池 reset：本 boot 0 次** | 日志里 reset 的成功/失败告警各 0 命中 ⇒ 该路径从未走过 |

**一句话策略**：**按 block 的全局 LRU、在分配需要块时按需驱逐**；
一个「只在两次请求之间共享、之后再无人用」的前缀条目，**它自己不会过期**，
只会被后续的分配压力挤掉 —— 所以**任何大规模测试流量都会把池冲过一遍**
（C 级换算：boot 以来材料化的新 KV 量约为池容量的 1.31–1.46 倍）。

### 1.5 ⚠️ 反直觉：`--prefix-cache-retention-interval` 会**加剧**驱逐压力

这个参数的名字容易让人以为「设大一点缓存就留得住」。**方向相反。**

| 事实 | 说明 |
|---|---|
| 默认值 | **0**（未设等价于 0） |
| 它治什么 | **SWA 组自身的复用深度**（让周期边界成为可复用的 checkpoint） |
| 它**不**治什么 | 「头能不能活到下几分钟」 |
| 为什么反而更糟 | 被保留的 checkpoint 块**带哈希** ⇒ 排在 free 队列**尾部**（最后被驱逐）⇒ **占住池、拉长不可驱逐区** ⇒ 留给新条目的块变少 ⇒ 老条目**更早**被挤掉 |

⇒ **不要把 retention 当作「治首步停顿」的手段。** 若要试，判据必须改成
**双判据（复用深度 + 条目寿命）**，且先准备好解释「为什么短期能命中、数分钟后为 0」这个矛盾。

### 1.6 怎么读「缓存命中」

- 用引擎返回的 `usage` 里的 **`cached_tokens`** 字段（需开启 `--enable-prompt-tokens-details`）。
- ⚠️ **口径**：如果某个字段叫 `inputTokens`，它往往是「**全量 − cached**」（**未缓存**量），
  不是全量 prompt。三个数要摊开写：**全量 prompt | cached | 未缓存**。
  把 `inputTokens` 当「全量」会让结论全错。
- 累计命中率可在 `/metrics` 的对应计数器上读增量，逐位对账（`Δhit = n × 单次命中量`）。

## 2. ⭐ 运行时行为：带 tools 时引擎会强制保留历史思考

这一节是一条**引擎行为**，不是参数问题，但会显著影响你的延迟预算。

### 行为

引擎里有一段逻辑（源码级，A 级）：

```python
# 只要**任一**消息带 tools，就关掉「丢弃历史思考」的优化
effective_drop_thinking = drop_thinking
if any(m.get("tools") for m in full_messages):
    effective_drop_thinking = False
```

也就是说：**本来会**从历史里丢弃旧的 thinking 块，但**只要请求带 tools 就强制不丢**。

### 影响

客户端（尤其是 agent 类应用）每轮都带几十个 tool 定义 ⇒ 每步都把累积的 thinking 全文重新渲进 prompt
⇒ 新增 token 量被撑大 ⇒ **每个 step 起始出现数秒的硬停顿**。

实测（真实会话数据）：

| 现象 | 实测 |
|---|---|
| 停顿量正比于 | **该步新增的总 token 数**（不是工具返回量） |
| 新增 token 的构成 | 上一步的输出约占 **61%**，其余（工具返回等）约 **39%** |
| 等效 prefill 速率 | 约 **1,400–2,600 tok/s**（即新增部分被**全量重算**） |
| 停顿分布 | 51 个 step 中：`<2s` 23 个、`2–5s` 11 个、`5–10s` 4 个、`>10s` 13 个 |

### 应对（按杠杆大小）

| # | 做法 | 有效性 |
|---|---|---|
| 1 | **减少工具返回体积**（截断工具输出、别一次读大文件、别在一个 step 里并发多个读/多机 SSH） | 中（占新后缀 39%） |
| 2 | **减少 step 数**（每个 step 都是一次完整 prefill；让单 step 产出更大） | 中 |
| 3 | 减少工具定义体积 | 小（只影响**首请求**，在缓存前缀里） |
| ❌ | 调「思考档位」（reasoning effort） | **无效** —— n=3 复测：档位之间无单调关系，同档位方差达 2.4×；`dIn ≈ 上一步出字量 + 约 170` ⇒ **停顿量由「上一步出字量」决定**，档位管不住 |
| ❌ | 调 `--max-num-batched-tokens` | **无效** —— ttft 正比于**总新增 token**，正比于**块数**的模型被实测证伪 ⇒ 改 MAXB 只改「每块大小」，不改单请求 prefill 总时长 |

### ⚠️ 一条通用教训

「某个旋钮看起来应该有效」**不等于**「它接在待测链路上」。
上面两条被否证的假设都是**先做了设计、跑了机时、才发现旋钮没接线**。
**在花小时级机时之前，先用一个「旋钮拧到底」的廉价探针证明它有响应。**
